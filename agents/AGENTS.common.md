# Shared AI-agent conventions (isejalabs)

This file is imported into each consuming repo's own `AGENTS.md` (`CLAUDE.md` symlinked to it) via Claude Code's `@path` import syntax, after adding this repo as a git submodule. It holds conventions that are genuinely identical across multiple isejalabs repos — repo-specific conventions (architecture, domain, build commands) stay in the consuming repo's own `AGENTS.md`, never here.

## Commit messages

Follow Conventional Commits with a path-derived scope: `type(scope): subject`, e.g. `feat(module-name): ...`, `fix: ...`. Scope is typically the primary directory/module/component the change touches; omit it (just `type: subject`) when a change spans multiple areas and isn't specific to one. **Never reference an issue in a commit message, in any form** — not a closing keyword (`Closes #123`/`Fixes #123`), not a plain reference (`Relates to #123`, `see #123`, `part of #123`), not a bare `#123` in prose. This applies to every commit pushed on the branch, not only whatever ends up on the default branch: GitHub auto-links a bare `#N` and fires a "mentioned in commit" cross-reference on the issue's timeline the moment the commit is *pushed to any branch*, independent of whether it's later squashed or rebased away — so an intermediate commit that never lands on `main` still leaves a permanent mark on the issue, and amending/rebasing that same commit during review fires a *second*, duplicate cross-reference for the new SHA. Issue references belong in the PR description alone (see the closing-keyword exception under PR discipline below, which applies there, not to commits).

Use scope `ai` (`docs(ai): ...`) for changes to `AGENTS.md`/`CLAUDE.md` itself — instructions aimed at AI agents rather than repo documentation in general. Use `ai/<skill>` (`docs(ai/<skill>): ...`) when the change is scoped to one skill under `.agents/skills/<skill>/` (`.claude/skills` is symlinked the same way).

## PR discipline

- **Never push directly to `main`** (or any other protected/default branch) — always through a PR, regardless of size or how temporary the change is meant to be.
- **Prerequisite items**: if something must happen before an action can be taken — merging a PR, closing an issue, applying a plan-based change — never assume it's done just because it was mentioned earlier or the user said "looks good". For a PR, list it under a `## Before merging` heading in its body as a checklist; the same rule applies to a prerequisite stated in a standalone issue or plan, PR or not. Before taking the dependent action, list each item back to the user explicitly and get per-item confirmation — a general go-ahead doesn't count. This is agent-mediated: it applies whenever an agent performs the action, including via CLI — only a human bypassing the agent entirely skips it. Once an item is confirmed, check it off in the PR body as part of the same action.
- **Recording a "blocked by" relationship**: when one issue genuinely can't be worked/closed until another lands, set it up as a real GitHub issue relationship via `gh api graphql` (`addBlockedBy`, taking `issueId`/`blockingIssueId` node IDs from an `issue(number: N) { id }` query) — this only accepts Issue nodes on both sides, rejecting a PR's node ID outright. When either side is a PR, fall back to the `## Before merging` checklist convention instead.
- **Recording a "sub-issue" relationship**: when splitting one issue into several (a phased plan, an umbrella tracking issue), link each part as a real GitHub sub-issue of the parent — not just a text mention — via `gh api repos/<owner>/<repo>/issues/<parent-number>/sub_issues -f sub_issue_id=<id>`, where `<id>` is the sub-issue's REST `id` field, not its issue number (get it via `gh api repos/<owner>/<repo>/issues/<sub-number> --jq .id`). Do this proactively when creating the sub-issues, not only when asked to fix it afterward (real precedent this was missed on: [isejalabs/homelab#1388](https://github.com/isejalabs/homelab/issues/1388)).
- **Keep a short reference to each sub-issue in the parent's own body**: when an issue's action-item checklist gets turned into sub-issues, don't delete the corresponding checklist line — leave a short reference on it instead (e.g. `- [ ] Phase 2: external-dns (see #1384)`). GitHub's own "Sub-issues" progress section already tracks them separately, but the parent issue's body should still read coherently on its own without requiring a reader to cross-reference that section.
- **Linking to an issue/PR in a repo we don't own** (a third-party/upstream repo, e.g. `kubernetes-sigs/external-dns`): use a short link through `redirect.github.com` instead of a plain `github.com` link, e.g. `[owner/repo#123](https://redirect.github.com/owner/repo/pull/123)`. A plain link creates a "mentioned this pull request" cross-reference on the *target's* timeline — unwanted noise on a repo that isn't ours; the `redirect.github.com` form resolves the same for readers without triggering that notification. This does **not** apply between repos we do own/control — any `isejalabs` org repo, or the personal `sebiklamar` account — a plain link there is fine, and the resulting cross-reference is a useful signal, not noise, since we see both sides of it.
- **Always format references to GitHub issues, PRs, and CI jobs/runs as markdown links**, not bare numbers or plain text — e.g. `[#1234](https://github.com/owner/repo/issues/1234)` — wherever one appears in a chat reply, PR/issue body, or comment, so it's directly clickable. Exception: a closing keyword in a PR body (`Closes #123`, `Fixes #123`, `Relates to #123`) stays as the bare reference, since GitHub only auto-links/auto-closes on that exact form — this exception is for the PR body only and never extends to a commit message (see the Commit messages section above).
- **Branch naming and the issue-first prerequisite for any new branch** — see `branching.md` in this same folder.
- **Test plan**: a PR includes a `## Test Plan` checklist in its body — tests identified while making the change, plus any the user adds during review — and every item gets ticked off (by actually running/verifying it, not just checking the box) before the PR is called mergeable.
- **Documentation check, once right before merge**: before calling a PR mergeable, check whether the change needs any documentation update — a README/index entry, an operational doc, a comment on a new function — and fold it into the same PR if so. Do this once, right before declaring the PR ready, not again after every incremental commit added to it in the meantime. Real precedent this was missed on: new scripts shipped with no index entry and inconsistent function-comment coverage, caught only after merge — see [isejalabs/homelab#1446](https://github.com/isejalabs/homelab/issues/1446).
- **Title every PR itself in Conventional Commits form** (`type(scope): subject`, same convention as commit messages above) at creation time, not just its underlying commits. GitHub's squash-merge defaults to the PR title (plus an auto-appended `(#<n>)` suffix) as the commit subject unless explicitly overridden — a plain-English PR title (e.g. "Fix the thing") becomes a non-conventional commit on the default branch the moment anyone merges without manually retyping the subject, which is exactly what happened at [isejalabs/homelab#1399](https://github.com/isejalabs/homelab/pull/1399): the commit message itself was conventional, but the PR title wasn't, and merging with the default subject carried that straight onto `main`.
- **Merging**: repos following the `github/` merge-commit convention (see the root of this repo) reject a plain merge commit outright — always squash-merge (falling back to `rebase` only if squash is also disabled), never a plain merge commit, even where one would technically be accepted. Keep GitHub's auto-appended `(#<n>)` PR-number suffix on the squash-commit title, but keep the PR title itself short enough that the full title (suffix included) stays within the conventional ~72-character commit-subject limit. Replace GitHub's default squash-commit body prefill (the concatenation of every individual commit message) with a condensed summary instead: a short top-line recap of what changed, plus optional brief details only where the PR description doesn't already cover them — don't restate the full PR body, since it's one click away. If the PR carries a Claude Code attribution trailer (`Co-Authored-By:`/`Claude-Session:`), keep that trailer in the squash-commit body rather than letting GitHub's prefill drop it.

## Markdown formatting

- **No manual line breaks within a Markdown paragraph** — whether a repo `.md` file (docs, READMEs) or a GitHub issue/PR body. Write each paragraph as a single line and let the editor/terminal/renderer soft-wrap it for display; only break the line for an actual paragraph break (blank line), a list item, a heading, or a code block. A hard-wrapped paragraph renders identically on GitHub (a single `\n` collapses to a space) but makes diffs noisy — editing one word near a wrap point reflows and diffs the whole paragraph instead of just that line.
- **Never backslash-escape backticks (or other Markdown punctuation) in a GitHub issue/PR/comment body.** Post the body as plain Markdown text exactly as it should render — an inline code span is a literal `` `foo` ``, never `` \`foo\` ``. This tends to happen when a body is drafted or previewed via a Bash heredoc, where backticks must be escaped there to stop the shell from treating them as command substitution, and then posted through a tool call (`gh issue create`, `add_issue_comment`, etc.) with that shell-escaping still attached — those tool parameters are plain strings with no shell involved, so draft the text directly, or strip the escaping back out before it goes into the call. Seen recurring specifically for `gh issue create`/`gh issue edit` more than `gh pr create` (e.g. [isejalabs/homelab#1275](https://github.com/isejalabs/homelab/issues/1275)) — a correct, unescaped worked example is typically given for PR creation but not for issues, so issue bodies get drafted ad hoc and over-escaped more often. Use the same pattern for issues as for PRs: a single-quoted `'EOF'` heredoc delimiter (`gh issue create --body "$(cat <<'EOF' ... EOF )"`) means the shell won't touch `` ` `` or `$` inside it, so inline code spans and fenced code blocks go in verbatim, unescaped.
